# 好学 — REQUIREMENTS

## 1. 产品目标

好学是一个 Personal Learning Agent。它通过学生的真实学习行为建立长期知识状态，并根据该状态主动决定下一步教学或练习行为。

比赛版必须完成的最小价值证明：

> 扫描真实选择题作业 → AI 找到错题与薄弱知识点 → 自动形成 Evidence / Knowledge State → Tutor 根据回答改变教学方向 → 完成练习后掌握度更新。

---

## 2. 用户与范围

### 用户

- 单用户；
- 不需要多账号系统；
- 不需要复杂权限模型；
- Demo 可默认进入固定用户。

### 学科范围

P0 仅支持：

- 高中数学；
- 导数基础；
- 选择题。

UI 可以展示其它学科的模拟数据，但不得将其描述为已实现真实能力。

---

## 3. 功能需求

### 3.1 首页

首页需要回答三个问题：

1. 我现在学得怎么样？
2. 哪个地方最需要关注？
3. 下一步应该做什么？

必须包含：

- Next Step；
- 知识掌握摘要；
- 错题入口 / 最近错题；
- 可选的最近学习变化。

### 3.2 扫描 / 上传

统一称为“扫描”或“上传图片”。

用户不需要预先选择：

- 上传作业；
- 上传试卷；
- 上传不会做的题。

后端根据内容自行理解。

要求：

- 使用系统相机 / 文档扫描能力；
- 前端只进行页面透视矫正，使拍歪的纸张变直；
- 支持一次添加多张照片；
- 已添加照片后可以继续点击 **“上传更多”** 追加图片；
- 前端不做复杂 OCR 或题目理解；
- 图片上传后显示分析状态与进度。

### 3.3 AI 分析

后端负责：

- 识别题目；
- 识别选项；
- 判断学生选择；
- 判断正确 / 错误；
- 映射知识点；
- 分析错误原因；
- 形成结构化结果；
- 创建 Evidence；
- 必要时加入错题库；
- 更新 Knowledge State。

### 3.4 错题库

错题不只是照片收藏。

每道错题应尽量关联：

- 题目；
- 来源；
- 学生答案；
- 正确答案；
- 知识点；
- 错误类型；
- AI 诊断；
- Evidence。

### 3.5 Knowledge State

Knowledge State 必须由 Evidence 驱动，而不是让 LLM 任意生成百分比。

Demo 示例：

```text
数学
└── 导数 57%
    ├── 基础求导 91%
    ├── 导数符号 78%
    └── 单调性 43%
```

前端不计算掌握度，只展示服务器返回值。

### 3.6 Tutor

Tutor 不是普通聊天框。

比赛版交互：

- LLM 输出教学文字；
- A / B / C / D 为结构化选择项；
- UI 保留“写下你的想法……”输入框；
- **当前 Demo 中自由输入不上送后端，可视为 `none` / disabled behavior；**
- 用户选择后点击“继续”，再提交给后端；
- 后端根据选择结果实时改变下一步引导。

Tutor Session 应体现 RPG 式分支感，但不使用游戏化视觉元素。

### 3.7 Practice

练习以导数基础选择题为主。

服务器负责：

- 提供题目；
- 校验答案；
- 产生 Evidence；
- 更新 Knowledge State；
- 返回下一步建议。

### 3.8 草稿本

Tutor / Practice 页面右上角提供“草稿本”。

要求：

- 使用 PencilKit；
- 打开时背景虚化 / 降低视觉权重；
- 支持 Apple Pencil 与常规触控书写；
- 提供一键清空；
- 清空前必须二次确认；
- 比赛版不要求 AI 理解草稿内容。

### 3.9 设置

设置页可包含：

- 图书商店 / 题库展示；
- 订阅 / 学习额度展示；
- Screen Time / 专注模式；
- 数据与隐私；
- About This App。

商业功能仅需表达意图，不要求真实支付；Hackathon 版本可完全由 iOS 前端本地 Demo State 实现，不要求后端商业接口。

---

## 4. 商业 Demo 需求

- 初始赠送 1,000,000 学习额度；
- 可展示购买学习额度；
- 可展示订阅模式；
- 可展示图书序列号 / 图书解锁概念；
- 所有价格与额度数据在 Hackathon 中都允许为 Demo 数据；
- 图书商店、订阅、额度与解锁状态允许仅存在于前端，不要求服务端持久化；
- 不在比赛阶段实现 StoreKit、复杂计费算法或真实结算。

---

## 5. 非功能需求

### 稳定性

- 现场 Demo 必须有可重复执行的稳定联网路径；
- 对网络错误、AI 超时或服务端失败提供明确错误状态与可重试入口；
- Mock Data 主要用于 Preview、UI 测试与开发调试，不要求承担离线演示兜底。

### 性能

- UI 转场尽量保持流畅；
- 图片上传前可进行合理压缩；
- 不做无意义的大图缓存。

### 安全

禁止提交：

- API Key；
- LLM Key；
- 数据库密码；
- 私密协作 Token；
- 用户隐私数据。

### 可维护性

- iOS 与 Backend 必须通过 API Contract 解耦；
- SwiftUI View 不直接依赖具体模型 Provider；
- 后端 Prompt / Provider 替换不应要求大改 iOS UI。

---

## 6. Definition of Done

比赛版完成必须满足：

1. App 可正常启动并进入 4 Tab；
2. 首页核心学习状态与 Next Step 来自真实后端；其它未实现学科可使用明确标识的 Demo 数据；
3. 扫描页能添加、预览、追加图片；
4. 至少一次真实后端分析能够跑通；
5. 错题 / 知识点结果能显示；
6. Tutor 可完成多轮 A-D 交互；
7. Agent 能根据至少一次错误选择改变后续内容；
8. 至少一次学习后出现掌握度变化；
9. 草稿本可写、可清空、清空有确认；
10. 现场联网环境下，完整 Demo Flow 可稳定重复执行。
